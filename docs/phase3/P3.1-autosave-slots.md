### P3.1 — Autosave, manual slots, and portable saves `TODO`

**Goal.** Make campaign continuity invisible when it should be and deliberate when it matters.
The player should safely return after a refresh or interruption, while retaining named checkpoints
for experiments and difficult choices.

**Depends on.** P3.0.

**Save policy.**

- Maintain one rolling autosave per scenario/player-party pair. It is an implementation detail,
  not a slot the player has to manage.
- Queue an autosave only after a domain transaction completes: day tick, event choice, P2.8
  contest action/result, P2.9 lever action, election result, and manual resume/return-to-menu
  boundary. Do not save an action half-applied.
- Debounce bursts of non-critical writes, but flush pending work on `visibilitychange` when the
  document becomes hidden and on `pagehide`. Do not claim a browser-close event is guaranteed.
- Manual saves are named slots with a short, editable label and immutable metadata (scenario,
  party, simulated date, real-world modified date, and thumbnail-free summary such as polling/
  cash). Confirm overwrites and deletions.
- Provide JSON export/import as an optional local portability feature. Imported data is decoded
  through the P3.0 validator, cannot overwrite an existing save without confirmation, and never
  executes code or trusts an arbitrary prototype.

**Steps:**

1. Build an autosave scheduler in the save coordinator. Subscribe only to completed, typed domain
   actions—not broad deep-watches over stores—so it has a clear causal boundary and no save loop
   during hydration.
2. Add `saveNow`, `createManualSave`, `renameManualSave`, `deleteSave`, `exportSave`, and
   `importSave` commands. Surface `saving`, `lastSavedAt`, and recoverable write/import errors to
   the UI without blocking a live campaign for ordinary delayed writes.
3. Write an atomic-replacement strategy appropriate to IndexedDB: construct/validate the complete
   record before replacing the previous autosave. A failed write must leave the prior autosave
   available.
4. Add a compact save-status affordance to the game HUD: “Saving…”, “Saved”, or an unobtrusive
   retry/error state. It must announce status changes accessibly and never imply a save succeeded
   before the repository resolves.
5. Build a save-management panel usable from the in-game pause/menu surface. It lists manual
   slots, supports save/rename/delete/export, and offers import. Destructive actions require an
   explicit confirmation dialog with keyboard focus handling.
6. Test scheduler coalescing, required trigger points, no writes during hydrate, failed-write
   recovery, manual-slot metadata, export/import round trips, duplicate import handling, and
   page-visibility flush invocation through an abstracted browser-event seam.

**Files:** new `src/save/autosave.ts` and tests; `src/stores/save.ts`; new save-management
components under `src/components/`; `src/components/GameClock.vue` or a new HUD status component;
the typed action sites in game/P2.8/P2.9 stores.

**Acceptance:** after a day, a lever action, and a contest action, refreshing the app offers a
restore point containing all three changes. Manual saves can be created, named, loaded, deleted,
and exported/imported without corrupting the rolling autosave. A failed storage operation leaves
the playable game and last successful save intact.
