### P3.5 — Election resolution and changing political world state `DONE`

**Goal.** Let elections alter the campaign world. P2.0's uniform-national-swing projection gives
the General Election result screen a credible win check; P3.5 turns scheduled elections and P2.8
contests into resolved outcomes that update playable state, produce a satisfying result moment,
and feed the next campaign period.

**Depends on.** P3.3 and P3.4. P3.0 is required because mutable seat-holder/outcome state must
save and restore. It builds on P2.0 projection and P2.8 election scheduling; it does not replace
their data acquisition.

**Decisions.**

- Static scenario composition remains a historical starting snapshot. Store a typed mutable
  representation overlay/outcome ledger for winners, turnover, and future election dates.
- The first implementation uses rules appropriate to the available data: Commons results extend
  P2.0's seat-level projection with local commitments; council/devolved/mayoral outcomes ship only
  once their electoral rules and data are sufficiently modelled. Do not pretend every tier has the
  same voting system.
- A projection is distinguishable from a resolved result. The player can inspect both, and the
  result screen says which model/data produced an estimate.

**Steps:**

1. Design `ElectionInstance`, `ElectionOutcome`, and mutable representation/outcome-ledger types.
   They identify tier, date, eligible seats/offices, result status, inputs/provenance, winners,
   swing/turnout fields where available, and concise outcome summaries. Link P2.8 contests into
   the same model rather than maintaining a parallel result format.
2. Extract/extend pure resolver modules per electoral system. For the Commons, combine baseline
   result, national polling swing, event/action impacts, and P3.4 local commitments in a bounded,
   deterministic calculation. Publish input summaries that are sufficient for a player to follow
   the result without exposing raw internal weights as UI clutter.
3. On an election date, pause the clock, create a pending resolution item, and present an election
   night/results sequence that can be sped through or skipped. Once confirmed, atomically apply
   the outcome ledger, party resource/momentum consequences, feed entries, and next-election
   schedule before allowing time to resume.
4. Update map and hemicycle region-state builders to read mutable representation state first and
   fall back to immutable scenario composition. Update party stat getters and win conditions to
   use the new current representation—not stale 2025 holders.
5. Expand `ResultScreen.vue` into an election result view with seat change, majority threshold,
   decisive places, player objective status, and clear options to continue, save, or return to the
   menu. A GE result remains a headline moment, not an accidental dead end.
6. Define post-election consequences conservatively: a won/lost objective record, budget/momentum
   changes, scheduled leadership/campaign resets, and a next electoral horizon. Government policy
   simulation is a separate future design; do not imply it exists here.
7. Test resolver invariants (every eligible seat has one valid winner; counts reconcile; no double
   application), same-seed result replay, save before/after resolution, result UI transitions, and
   current-map composition after applied outcomes.

**Files:** new `src/types/election.ts`, `src/sim/elections/` modules and tests, game/campaign
store, `map/regionState/*`, `PartyPanel.vue`, `HemicycleView.vue`, `ResultScreen.vue`, and P2.8
state integration.

**Acceptance:** resolving an eligible election produces one deterministic, inspectable outcome;
the map, hemicycle, party statistics, feed, save game, and future objectives all reflect it after
a refresh. The result cannot be applied twice, and seat totals reconcile to the tier total.
