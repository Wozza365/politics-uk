### P3.9 — Balance, deterministic regression, and performance hardening `TODO`

**Goal.** Ensure a feature-rich campaign remains fair, reproducible, and responsive. Balance is
not a final spreadsheet pass: every new action, scenario, opponent choice, and election model
needs a safety net against an unwinnable or trivial game.

**Depends on.** Starts with P3.0 and expands as P3.3—P3.6 land. It is a continuous task with an
initial implementation milestone, not a reason to hold all gameplay until the end.

**Steps:**

1. Define a headless deterministic campaign runner that can initialise a scenario, advance days,
   supply scripted player/AI actions, resolve pending decisions, and return a compact outcome
   report. It imports the same pure/store orchestration used by the app; do not build a divergent
   “test-only simulation.”
2. Create committed regression fixtures for representative parties/difficulties and key campaign
   states: first campaign month, an active P2.8 contest, large party vs small party strategy, GE
   resolution, and save/restore mid-campaign. Assert invariants and stable summaries rather than
   brittle incidental feed wording.
3. Establish measurable balance indicators: resource solvency, action availability, polling range,
   contest win rates, election outcomes, and objective completion. Run fixed-seed batches across
   scenarios/difficulties and review distributions whenever tunable data changes. Flag impossible
   progress and dominant no-risk strategies; tuning remains a human game-design decision.
4. Add property/invariant tests: vote/seat totals reconcile, resource values remain within defined
   bounds, no outcome is applied twice, cooldowns expire, all saved references resolve, and repeated
   runs with the same seed/actions match exactly.
5. Profile actual production builds with the largest map/tier data and populated feed/history.
   Establish budgets for initial load, view switch, map interaction, autosave latency, and memory.
   Use dynamic imports/caching/virtualised lists only where measurements show a need; preserve the
   `MapRenderer` abstraction.
6. Add a release checklist: clean new-game path, save/import compatibility, no-save recovery,
   a keyboard campaign smoke test, accessibility manual matrix from P3.8, and scenario-data
   validation/provenance review. No analytics or player data collection is required for this work.

**Files:** new `src/sim/campaignRunner.ts` and tests, test fixtures/reports, performance notes or
scripts, `package.json` commands if justified, CI configuration if present, and a release checklist
under `docs/`.

**Acceptance:** fixed-seed campaign fixtures replay deterministically in automated tests; batch
reports expose the agreed balance indicators; core invariant failures are caught before release.
The largest supported scenario can be loaded, saved, restored, and switched between its supported
views within documented performance budgets on the agreed baseline device/browser.
