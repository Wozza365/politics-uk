### P3.0 — Versioned save-game contract and persistence repository `TODO`

**Goal.** Define one trustworthy, versioned representation of a live campaign and one browser
persistence boundary before any autosave or load UI is built. P2.8 introduces generated contests;
P2.9 introduces persistent player choices and resources. A direct `JSON.stringify` of Pinia state
would be fragile, leak transient UI state into old saves, and make future migrations needlessly
hard.

**Depends on.** P2.8 and P2.9. It is deliberately independent of the menu redesign in P3.2.

**Decisions.**

- A `SaveGame` contains `formatVersion`, stable save id, scenario id/revision, kind (`autosave` or
  `manual`), timestamps, optional player label, deterministic playthrough seed, and a typed
  `state` payload.
- The payload is a projection of *mutable* campaign state: date/clock settings, selected party,
  polling/history, queued and resolved event state, salience, P2.8 contest/vacancy state, P2.9
  finance/membership/staff/policy/campaign/leadership state, outcome history, and any mutable
  seat-holder overlay introduced by P3.5. It may include a small UI-restoration preference such as
  selected map view, but never an open modal or a running timer.
- Static scenario data, map boundaries, component instances, derived getters, and duplicated feed
  presentation are not authoritative save data. Rebuild them from the scenario and typed action
  history/state when hydrating.
- The current simulation uses keyed deterministic randomness. Save the playthrough seed now; any
  P2.8/P3 code which needs sequential randomness must store its cursor/state explicitly rather
  than relying on ambient `Math.random()`.
- Use IndexedDB as the production storage engine, isolated behind a `SaveRepository` interface.
  An in-memory repository supports tests. A fallback may be added only if it preserves the same
  semantics and storage-size limits are made clear.

**Steps:**

1. Create `src/types/save.ts` with discriminated save metadata, `SaveGameV1`, save summaries for
   the load screen, a format-version union, and narrow validation error types. Export it through
   `src/types/index.ts`.
2. Identify every piece of mutable state in `game`, `ui`, and the P2.8/P2.9 stores. Add explicit
   `toSaveState()` and `hydrateFromSaveState()` actions (or a dedicated mapper) rather than
   granting the repository direct access to store internals. Hydration must reset transient timer
   state, close menus, validate referenced party/tier/seat ids, and leave the clock paused.
3. Implement pure migration and validation functions in `src/save/codec.ts`:
   - parse untrusted JSON into an unknown value;
   - validate the outer envelope and scenario id before use;
   - migrate every supported older version to the current domain representation;
   - reject future/unsupported versions with a recoverable message;
   - normalise/clamp only values where a documented migration permits it; never silently turn a
     malformed campaign into a different one.
4. Implement `SaveRepository` in `src/save/repository.ts` and an IndexedDB implementation in
   `src/save/indexedDbRepository.ts`. Required methods are `list`, `read`, `write`, `remove`, and
   `clearAutosave`; writes replace a whole validated record and return metadata. Keep database
   name, store name, and indexes in one module.
5. Add a `useSaveStore` or similarly narrow coordinator responsible for repository lifecycle,
   selected save metadata, user-facing recoverable errors, and loading a save into the game/UI
   stores. It must not make components talk directly to IndexedDB.
6. Write unit tests for serialise → parse → validate → hydrate equivalence, corrupt records,
   unknown scenario ids, backwards migration fixtures, future-version rejection, and deterministic
   continuation after a restored save. Use the in-memory repository to test repository behaviour.

**Files:** new `src/types/save.ts`, `src/save/{codec,repository,indexedDbRepository}.ts`,
`src/stores/save.ts` (or a narrow composable); `src/stores/game.ts`, `src/stores/ui.ts`, and the
P2.8/P2.9 stores add explicit snapshot/hydration seams; focused `*.spec.ts` files.

**Acceptance:** an automated test starts a game, applies representative event, party-lever, and
contest changes, writes a save, creates fresh stores, restores the save, and observes the same
playable domain state. Corrupt/obsolete data does not crash the app or overwrite a valid save.
The restored game is paused until the player explicitly resumes it.
