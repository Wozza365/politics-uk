### P3.3 — Campaign action economy `TODO`

**Goal.** Turn P2.9's party controls and P2.8's contest choices into consequential campaign
management. The player should be deciding what *not* to do as often as what to do; no lever should
be a free, infinitely repeatable polling button.

**Depends on.** P2.8, P2.9, and P3.0 (the new state is persistent). P3.1/P3.2 are strongly
recommended for player-facing delivery but are not a logic dependency.

**Design boundary.** This task does not add new bespoke controls to each panel. It creates an
action-definition/action-resolution system that current and future UI can share. A party lever,
by-election effort, event response, and later opponent move use the same transaction pattern:
validate availability → pay costs → apply typed effects → record outcome → schedule autosave.

**Steps:**

1. Audit P2.9's fundraising, social-media, staffing, policy, campaigning, and leadership levers
   plus P2.8's `ignore`/effort actions. For each, write an `ActionDefinition` with a stable id,
   eligibility rule, costs, cooldown, duration, targeting requirements, predicted effect range,
   and deterministic resolution rule. Data belongs in scenario/simulation data; components own
   labels and accessible presentation only.
2. Establish the party resources that create meaningful trade-offs. The minimum is money, staff
   capacity, leadership attention, and time/turn capacity. Reuse P2.9 finance/membership where
   appropriate, but do not turn membership into a generic currency without an explicit model.
3. Implement pure `canTakeAction` and `resolveAction` functions under `src/sim/`. They return a
   typed result/denial, apply bounded deltas, register cooldowns/ongoing commitments, and queue
   `PollingImpact`s through the existing poll seam. Store actions enforce the result; Vue code
   cannot supply arbitrary numeric deltas.
4. Model ongoing commitments explicitly: campaigns, staff assignments, and leadership recovery may
   occupy capacity for multiple days, incur recurring costs, or be cancelled with a stated cost.
   Advance/expire them on the daily tick in a deterministic order.
5. Give every action a player-readable forecast and an after-action record: immediate known cost,
   duration, affected place/segment, and bounded uncertainty. Preserve source/action id on impacts
   so P3.7 can explain later poll movement.
6. Adjust P2.8/P2.9 components to consume the common action model. Include disabled reasons and
   an action confirmation only where an irreversible/high-cost action warrants it; routine actions
   should remain brisk.
7. Unit-test eligibility, caps, costs, cooldowns, multi-day commitment expiry, same-seed outcomes,
   and action denial. Add a store-level test proving a UI request cannot bypass validation.

**Files:** new `src/types/action.ts`, `src/sim/actions.ts`, action data under
`src/data/sim/` or scenario data, a party/campaign state store or focused additions to `game.ts`,
P2.8/P2.9 components, and `src/sim/actions.spec.ts`.

**Acceptance:** each existing lever and contest action has an explicit cost/opportunity cost,
availability state, and recorded outcome. A player cannot exceed available resources or repeat a
cooldown action; abandoning one strategy makes another feasible. The same saved state and action
sequence produce the same result.
