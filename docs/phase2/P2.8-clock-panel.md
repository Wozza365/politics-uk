### P2.8 - Expandable clock / by-elections panel `TODO`

**Goal.** Spec section 9.5: the clock UI is "an interactive element (expandable later to list
by-elections and other minor elections in detail)" - `src/components/GameClock.vue` (P1.9,
`PHASE_1_COMPLETED.md`) is currently a `disabled` button with an `aria-label` describing this as
a future stub.

This task owns the runtime election/vacancy surface. It should not try to pre-author every
possible by-election as a static `GameEvent`.

**Steps:**
1. Build a deterministic runtime by-election/minor-election scheduler rather than authoring every
   possible contest as static event-library content. The generic event library can still contain
   flavour events about "a by-election becomes symbolic", but the actual vacancies/contests should
   be generated from scenario seats, date, tier, party holdings, and seeded randomness.
   - Parliamentary by-elections: low-frequency, seat-specific rolls, capped/tuned to roughly 10 per
     year unless scripted vacancies override the cap.
   - Council by-elections: high-frequency rolls, potentially a few hundred per year across wards.
   - Other types (devolved, mayoral, PCC, etc.): separate per-tier rates because vacancy mechanics
     and political salience differ.
   - Use `src/sim/rng.ts` seeded determinism, never `Math.random()`, so the same playthrough seed
     produces the same vacancies.
2. Build the expanded panel/event-log presentation.
   - Parliamentary by-elections get full event-feed messages because each is nationally legible.
   - Council by-elections are grouped by week in the left event log, e.g. "18 council by-elections
     called this week", then expandable into individual actionable contests.
   - Each individual contest can be actioned separately; the player may focus resources on one seat
     but ignore another.
   - Before choosing an action, the player can drill down to the relevant map seat/ward and inspect
     current holder, previous results, majority, demographics, and local tier statistics.
3. Build the action model for contests. Each contest needs a small party-specific action set
   (`ignore`, `token effort`, `local push`, `nationalise the race`, etc. as appropriate) with
   effects on polling, momentum, local seat outcome probability, and possibly party resources once
   P2.9's expanded party panel exists. Not every party should get a meaningful response to every
   contest.
4. Per spec section 9.3/9.5, opening any menu pauses the game clock. `useGameClock.ts`'s existing
   pause-on-`pendingEvents` watcher (P1.9) establishes the pattern; reuse it rather than building a
   second pause mechanism. A generic `ui.openMenus` count watched by the clock composable would let
   this and P2.9's expanded party panel share one pause gate.
5. The expanded panel should list details of all upcoming elections the player can see coming, not
   just the next by-election: the next GE (P2.0), and once their data exists, devolved-parliament
   elections (P2.1), council/mayoral/PCC elections (P2.3/P2.4), in addition to random and scripted
   by-elections.

**Files:** `src/components/GameClock.vue`, `src/components/EventFeed.vue`,
`src/composables/useGameClock.ts`, `src/stores/ui.ts` (a shared "any menu open" flag), likely new
`src/sim/byElections.ts` / `src/types/election.ts` modules, plus store changes for generated
contest state.

**Acceptance:** clicking the clock opens a real by-elections/minor-elections panel and pauses the
clock while open; closing it resumes the clock. Parliamentary by-elections are generated as
individual feed items; council by-elections are grouped weekly but expandable/actionable
individually; selecting any contest can focus the map on that seat/ward and show the local
statistics needed before actioning.
