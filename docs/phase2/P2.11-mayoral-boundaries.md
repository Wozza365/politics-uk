### P2.11 — Mayoral boundary geometry `🔲`

**Goal.** P2.3 shipped `Mayoralty[]` as a stats-list-only feature: no mayoralty has boundary
geometry anywhere in this dataset, and `Mayoralty.regionRef` is just a free-text area slug (e.g.
`"greater_manchester"`) that doesn't resolve against any `geometryRef` in any `boundaries.*.json`
file — that was a deliberate scope call to avoid over-building a map layer for ~25 disjoint single
seats in one pass (see `PHASE_2_COMPLETED.md`'s P2.3 entry). This task is the follow-up: give
mayoralties real boundary geometry so `regionRef` can actually hover-link to the map.

**Depends on:** P2.3 (`Mayoralty` type, `fetch-mayors.mjs`, `mayoralties.json`) — this task only
adds geometry and the map-side wiring, it doesn't change the mayoralty roster itself.

**Steps:**
1. Source boundaries for the two different shapes mayoralties come in:
   - The ~11 combined-authority/CCA areas (Greater Manchester, West Midlands, Tees Valley, etc.)
     — ONS publishes Combined Authority boundary datasets (similar source family to
     `fetch-commons-boundaries.mjs`'s ONS Open Geography Portal pull); these are genuinely new
     geometry not derivable from existing constituency boundaries.
   - The 13 single-council local-authority mayoralties (Croydon, Lewisham, Watford, etc.) — ONS
     Local Authority District boundaries cover these directly.
   - London is the one partial shortcut: `boundaries.regional.json` already has all 75 Greater
     London Westminster constituencies (built for the Regional/London Assembly view per P2.1) —
     a "Greater London" outline could be derived by unioning those rather than re-fetching, if that
     proves simpler than a fresh ONS pull.
2. Decide the simplification/format following the established `mapshaper -simplify 10%
   keep-shapes -o format=topojson` step (`fetch-commons-boundaries.mjs`'s pattern) — don't skip
   this, even though ~25 shapes is small, for consistency with every other boundary set.
3. Set each `Mayoralty.regionRef` to the real `geometryRef` once it exists, replacing today's
   slug-only placeholder.
4. Decide how this surfaces on the map — most likely an overlay/toggle on the existing Regional
   view (colour each mayoral area by its current holder's party, on hover/click) rather than a new
   full-screen view, consistent with P2.3's "not a new view" steer. Combined-authority and local
   mayoral areas overlap each other and overlap Commons/Regional geography in complex ways (a
   combined authority spans several council areas; a council mayoralty sits inside a combined
   authority), so this needs its own design call on how to avoid a confusing layered map — record
   the decision once made.

**Files:** `scripts/data/fetch-mayoral-boundaries.mjs` (new), `src/data/scenarios/uk-2025-01-01/boundaries.mayoral.json`
(new), `scripts/data/fetch-mayors.mjs` (update `regionRef` values), `src/stores/scenario.ts`,
map/view wiring (exact location is this task's call, per step 4).

**Acceptance:** mayoralties have real boundary geometry and are visible/hoverable on the map (in
whatever form step 4 settles on), not just a count on the party panel; `npm run validate:data` and
`npm run build` clean.
