### P4.9 - Visual QA, performance budgets, and release packaging `DONE`

**Goal.** Close Phase 4 with evidence that the premium pass is robust: screenshots, contrast checks,
responsive checks, reduced-motion checks, performance measurements, and release-ready assets.

**Depends on.** Starts with P4.0 and finishes after P4.1-P4.8.

**Steps:**

1. Create a visual QA matrix covering title, new game, load, loading/restore, game HUD, expanded
   party panel, map hover/selection, by-elections, targeting, saves, help, explanation, hemicycle,
   result, and key empty/error states.
2. Capture screenshots at desktop, laptop, tablet/narrow, 320px width, 200% text zoom, and high
   contrast where available. Include at least one state with long party names, long constituency
   names, many save slots, and many feed entries.
3. Check contrast for token pairs, party card text, map labels/tooltips, disabled controls, focus
   rings, destructive actions, chart series, and overlay states. Fix failures or document a product
   decision with an alternate cue.
4. Check colour-blind and non-colour comprehension: party-heavy charts, map overlays, selection,
   warnings, success, contest states, player/opponent activity, and disabled regions.
5. Check reduced-motion and reduced-sensory modes: no unnecessary movement, no repeated pulse,
   no spinner-only state, and no essential information conveyed solely by animation or sound.
6. Measure visual-performance budgets on production builds: initial title render, scenario setup
   render, map first paint, map hover/zoom, view switch, panel open/close, save panel, and result
   reveal. Record baseline device/browser assumptions.
7. Review release packaging: favicon, app icon, title, metadata, screenshots, asset rights, visual
   changelog, and known visual limitations.
8. Run `npm run build`, `npm test`, and `npm run validate:data`. Add a screenshot/visual-regression
   command only if it provides maintainable value for this repo.

**Files:** new visual QA checklist/report under `docs/`, optional screenshot folders or references,
`public/` app assets, package scripts if a visual test command is added, and fixes across visible
components found during QA.

**Acceptance:** Phase 4 ends with a checked visual QA report, release-ready icons/assets, documented
performance numbers, and no known critical layout, contrast, reduced-motion, or responsiveness
failures. The production build and existing tests pass.

**Completion artifacts:** release QA is in [`P4.9-release-qa.md`](./P4.9-release-qa.md), with
screenshots and performance data in [`screenshots/p4-9/`](./screenshots/p4-9/).
